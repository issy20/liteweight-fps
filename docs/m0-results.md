# M0 測定結果（2026-09-27）

判定: **M0完了（2026-09-27）。M1以降の描画基盤にwgpu+winitを採用する。**

## 環境・条件

- macOS 15.6.1 (24G90)、Apple M1、RAM 8 GiB、開始前にAC電源・充電100%を確認。
- Rust 1.98.1、Release、Cargo.lock固定。wgpu/Metal、Miniquad/OpenGL `4.1 Metal - 89.4`。
- 表示先1920×1080、論理ウィンドウ960×540。内部描画720p/1080p、静的ダミー5/20。
- VSync on要求、各実装・条件で3回。warmup 5秒＋計測30秒。A→B / B→A / A→B。
- 初回セッションは15:39開始。最後の1080p/20体の組を除き18試行を採用。
  同組はフォーカス喪失と提示動作の異常により全て除外し、別セッションの6試行に置換。15:59終了。
- 取り直しと追加試験は`caffeinate -di`で測定中だけ画面・アイドルスリープを抑止。
- 熱状態、バックグラウンド負荷、ドライバーキャッシュは厳密に統制していない。
  ディスプレイの物理提示タイミングと入力遅延は未測定。送信FPSを表示FPSと同一視しない。

## 中断・除外の扱い

初回の1080p/20体の後半で、VSync on要求にもかかわらずMiniquadが約1347送信FPS、
次のwgpuが約1606送信FPSとなり、wgpuのフォーカス喪失チェックで自動停止した。
画面スリープ・非表示化が疑われるが、原因は確定していない。成功扱いのMiniquadデータも含め、
この組全体を除外した。元データは`results/m0-20260927/`に保存し、書き換えていない。
除外試行のJSONは[除外記録](benchmarks/2026-09-27/excluded/README.md)にも保持している。

これは`comparison_valid: true`だけでは実際の画面提示状態を保証できない例でもある。
再測定では画面スリープを抑止し、通常のフレーム間隔・両実装の表示寸法一致を確認した。

## 技術選定

**wgpu+winitを採用する。** FPSの優位性を理由にはしない。

- 固定内部解像度の描画が既存の公開APIで成立し、今回のmacOS実行でパイプライン検証エラーが出ていない。
- VSync on/offに対応する提示方式を選択・記録でき、今回offで挙動の変化を確認できた。
- Miniquad 0.4.11のMetal経路には確認済みの形式不一致、macOS OpenGL経路には描画スケジュール制約が残る。
- MiniquadのRSSの小ささは利点として記録し、比較実装を残す。

再評価条件: wgpu側の入力実機確認で問題が出る、対象GPU/OSの互換性が不足する、
実ゲームで性能・メモリ目標を満たせない、Miniquad側でMetalと提示制御の問題が解消する場合。
ユーザーによる両実装の目視・マウス操作確認も全項目合格し、M0の完了条件を満たした。
今回の変更はM0まで。M1以降の機能実装は別作業とする。
